## 2. 背景与问题证据

### 2.1 当前数据库事实

2026-09-11对本机`policyops`只读核对结果：

- `cases=36`，其中活动案例36条；`case_text`非空0条，`transcript_text`非空0条。
- `showcase_cases=36`，公开选中案例36条；`user_message`只有1个不同值，`ai_response`只有1个不同值。
- `tests=78`，由42条DSL example和36条地区回归测试组成。
- `policy_snapshots=10`，`jurisdiction_planning_releases=5`。
- 上海18条、广东18条的数量与策展配额存在，但内容不可作为可读案例交付。

### 2.2 根因

地区案例重建只把`input`、`expected`、`assertions`、`evidence`和质量字段写入`cases`，没有生成`case_text`；展示案例只写入以下统一占位内容：

- 用户问题：`确定性模板生成的政策案例（无真实用户数据）`；
- 系统回答：`由修复后的快照规划器计算期望`。

上海案例还有更深层的语义缺陷：虽然场景被标记为退休、养老、医保、失业、灵活就业和补贴六类能力，但18条案例的断言全部只覆盖法定退休年龄和退休日期。页面若直接按能力标签补写文案，会把规则引擎没有计算的结果描述成确定事实。

### 2.3 真实性问题

公开案例页仍使用“真实咨询记录”“真实社保规划案例”“真实咨询样本”等表述。当前36条是无真实个人数据的确定性合成场景，该表述违反以下项目不变量：

- 合成政策案例不得描述为真实用户案例；
- 规则引擎是政策数字结论的唯一计算来源；
- 政策事实必须能够定位到权威原文；
- 未由权威来源证明的政策含义不得由Agent推断。

## 3. 目标与非目标

### 3.1 目标

1. 为上海全部活动政策参数、表格和政策承载规则补齐可验证的官方原文引用。
2. 纠正2026-09-01时点已过期、错误或由转录语料推断的上海政策事实。
3. 补齐失业金金额与灵活就业月缴费两项规则能力。
4. 将案例生成器升级为`RCL-GEN-2.0`，继续生成上海18条、广东18条。
5. 让每条案例的能力标签、人物输入、规则输出、断言、问答文案和政策依据一致。
6. 在原`cases`、`showcase_cases`和`tests`表中受控写入V2内容，同时保留数据库行ID和完整前后审计链。
7. 公开页、管理后台、API、数据库与Markdown案例库使用同一份确定性内容。
8. 在独立功能分支完成开发和隔离验收，推送后等待用户测试，不自动合并目标分支。

### 3.2 非目标

- 不使用LLM生成政策数值、资格结论、结构化输入或期望结果。
- 不使用真实咨询记录、录音、视频、手机号、身份证号或其他个人数据。
- 不把合成案例伪装为真实用户咨询或政策原文。
- 不原地修改已发布政策实体或不可变快照。
- 不修改广东政策含义，不生成四川用户案例。
- 不在代码开发阶段写本机持久`policyops`数据库。
- 不自动批准政策draft、创建或切换持久快照、执行案例回填。
- 不创建PR，不合并`main`，不创建tag或Release。

## 4. 用户与使用场景

| 用户 | 需求 |
| --- | --- |
| 普通访客 | 查看明确标为合成的典型政策案例，理解输入条件、测算结论和政策依据 |
| 注册用户 | 从案例进入规划前，识别哪些结论可确定、哪些字段需要补充 |
| 政策管理员 | 在后台核对案例文档、结构化输入、规则断言、快照和官方原文 |
| 开发与审计人员 | 证明案例文案、规则输出、内容hash、政策证据和数据库写入一一对应 |

## 5. 总体原则

1. **证据先于规则**：没有权威原文，不得新增或纠正政策事实。
2. **规则先于文案**：案例中的数字和资格结论只能来自规则引擎输出。
3. **场景先于展示**：先形成完整输入、期望和断言，再生成自然语言问答。
4. **版本化而非覆盖**：政策实体、快照、案例UID和生成器均使用新版本表达变化。
5. **持久写入默认拒绝**：开发只交付代码、隔离证据和授权计划；持久执行另行授权。
6. **历史可恢复**：旧政策、旧案例内容、旧UID、旧hash、归档与备份必须继续可审计。

## 6. 上海官方原文与政策纠偏

### 6.1 来源范围

只允许使用已登记并启用的官方域名：

- 上海市政府：`www.shanghai.gov.cn`；
- 上海市人力资源和社会保障局：`rsj.sh.gov.cn`；
- 上海市医疗保障局：`ybj.sh.gov.cn`。

转载、问答社区、搜索摘要、媒体报道和非官方公众号只能作为发现线索。规范性文件存在时，政策问答或解读不得替代规范性文件；解读材料可以作为独立的解释证据附加。

### 6.2 证据工件契约

每份政策文档在仓库中保存独立目录，至少包含`original.html`或官方附件、`extracted-text.txt`、`http-headers.txt`和`meta.json`。

`meta.json`必须记录`docId`、标题、发布机关、初始官方URL、最终URL、HTTP状态、抓取时间与方式、原件SHA-256、字节数和解析版本。

DSL中的每个evidence必须满足以下结构：

```json
{
  "document_id": "DOC-SH-...",
  "jurisdiction_code": "310000",
  "title": "正式文件标题",
  "authority": "发布机关",
  "official_url": "https://...",
  "fetched_at": "ISO-8601",
  "content_sha256": "64位小写十六进制",
  "artifact": "docs/.../original.html",
  "parse_version": "...",
  "locator": {
    "type": "article|section|paragraph|body",
    "reference": "条款或正文定位"
  },
  "excerpt": "逐字存在于extracted-text.txt中的短摘录"
}
```

### 6.3 引用覆盖范围

- 上海加入现有citation contract扫描范围。
- 当前上海27个活动参数/表格、8条地方规则以及本Feature新增规则全部纳入校验。
- 计算框架规则可以在明确白名单中免除政策引用；承载政策条件、数值、比例、期限或资格含义的规则不得豁免。
- 活动上海政策资产引用覆盖率必须为100%。
- 任一原件缺失、SHA不符、URL不符、摘录无法定位或有效期不明确时，上海V2快照不得发布。

## 7. 上海规则能力补齐

### 7.1 目标输出

| 能力 | 必须由规则引擎产生的输出 |
| --- | --- |
| 退休 | 法定退休年龄年/月、法定退休日期 |
| 养老 | 最低缴费年限、累计月数、缺口月数、缺口年数 |
| 医保 | 退休所需年限、缺口月数、等待期、等待期豁免状态 |
| 失业 | 领取资格、领取期限、领取阶段、当前月标准 |
| 灵活就业 | 使用的缴费基数、养老月缴费、医保月缴费、月合计 |
| 补贴 | 适用资格、补贴类别、估算金额、可享期限或需确认事项 |

### 7.2 新规则

#### R-SH-UI-AMOUNT

- 输入：失业金领取资格、已领取月数或当前领取阶段、as-of日期。
- 参数：as-of日期有效的三档失业金标准。
- 输出：领取阶段与`calc.unemployment.monthly_amount_est`。
- 缺少领取阶段、领取资格不确定或日期无有效参数时，不估算金额并设置`needs_agent`。

#### R-SH-FLEX-CONTRIBUTION

- 输入：灵活就业状态、本人选择的缴费基数；案例允许使用当期最低基数作为明确示例。
- 参数：当期缴费基数上下限、灵活就业养老费率、医保费率。
- 输出：规范化缴费基数、养老月缴费、医保月缴费和合计月缴费。
- 基数低于下限或高于上限时不得静默截断；必须返回可定位警告并要求确认。
- 缺少基数、费率或有效期参数时设置`needs_agent`。

## 8. RCL-GEN-2.0案例设计

### 8.1 总量与策展配额

- 总计36条：上海18、广东18。
- 每地区男性9、女性9。
- 每地区`before_1970`、`1970_1979`、`from_1980`各6条。
- 每地区`employed`、`flexible`、`unemployed`各6条。
- 不生成CN或四川用户案例。

### 8.2 上海能力矩阵

上海包含退休、养老、医保、失业、灵活就业缴费和补贴六种能力，每种能力3条。每种能力分别包含`employed`、`flexible`、`unemployed`各1条，从而每个就业状态合计6条。

为同时满足性别和年龄段配额，生成器使用固定能力顺序和轮转矩阵：

1. 能力顺序：`retirement`、`pension`、`medical`、`unemployment`、`flexible`、`subsidy`。
2. 就业状态顺序：`employed`、`flexible`、`unemployed`。
3. 年龄段索引：`(能力索引 + 就业状态索引) mod 3`。
4. 性别：`(能力索引 + 就业状态索引) mod 2`，偶数为male，奇数为female。

该矩阵必须产生性别×年龄段×就业状态的18个唯一组合。能力不适用于某个状态时，应验证“不适用”或`needs_agent`输出，不得伪造正向资格。

### 8.3 上海场景最低断言

| 能力 | 最低断言要求 |
| --- | --- |
| retirement | 退休年龄月数或退休日期 |
| pension | 最低缴费年限与缺口之一 |
| medical | 医保年限缺口、等待期或豁免状态之一 |
| unemployment | 资格、期限或金额之一 |
| flexible | 养老、医保或合计月缴费之一 |
| subsidy | 资格、金额、期限或补贴选择之一 |

非退休能力不得仅使用`calc.retirement.*`断言通过验收。

### 8.4 广东场景

- 保留现有18条和策展配额。
- 继续覆盖2030医保年限、2026地市医保年限缺参、广州失业金金额、领取地市缺失和缴费基数边界。
- 2030医保场景as-of日期保持2030-01-01；其余常规场景保持2026-09-01。
- 将泛化evidence替换为现有仓库中已验证的广东正式政策证据。

### 8.5 人物输入

- 需要精确退休日期的案例必须提供`birth_year`、`birth_month`、`birth_day`和`birth_date`。
- 女性必须明确`female_retire_type`；不允许由文案猜测工人或干部口径。
- 失业案例必须明确就业状态、失业保险累计年限及领取阶段或已领取月数。
- 灵活就业案例必须明确缴费基数。
- 补贴案例必须明确就业困难认定、距退休月数及相关就业/领取状态；缺失字段必须形成追问而非默认值。

## 9. 案例文档与展示内容

### 9.1 UID与版本

- 案例UID：`RPC-<地区>-<场景键>-V2`。
- 回归测试UID：`RPCT-<地区>-<场景键>-V2`。
- 生成器版本：`RCL-GEN-2.0`。
- V1行未来受控改写后升级为V2 UID，但数据库整数ID保持不变。

### 9.2 cases字段

- `case_text`：非空Markdown文本，包含合成声明、人物条件、咨询目标、计算时点和结论边界。
- `transcript_text`：保持NULL，禁止生成虚构转写。
- `topics/tags`：由实际能力、地区、性别、年龄段、就业状态和风险状态确定。
- `input/expected/assertions`：完整保存引擎输入和可比较输出。
- `evidence`：保存结构化政策来源。
- `snapshot_hash/content_hash`：按V2完整行内容重新计算。

### 9.3 showcase_cases字段

- 标题必须描述地区、人物特征和实际能力，不使用UID占位标题。
- `user_message`必须是自然语言咨询问题，36条不得全部相同。
- `ai_response`只能根据`expected/assertions`渲染；金额、月份和资格不得从标题或模板常量单独生成。
- `category`与实际能力一致。
- 保持`case_uid/source_case_uid`一一对应。

### 9.4 回答结构

每条公开回答依次包含结论摘要、关键测算结果、使用的个人条件、政策依据、缺失或需确认事项，以及“本案例为合成演示，不构成个案办理决定”声明。

### 9.5 Markdown案例库

未来实施需生成`docs/refactor/policy-ops-agent/case-library/shanghai-guangdong-v2.md`，包含全部36条的UID、地区、能力、日期、合成人物画像、问题、引擎结论、断言、快照和政策依据。

文档必须由确定性脚本生成并支持`--check`模式；手工修改导致与manifest不一致时测试失败。

## 10. API与UI契约

### 10.1 API兼容性

现有案例字段保持兼容，公开与管理响应新增：

```ts
type CaseNature = "synthetic" | "human_curated";

interface PolicySource {
  documentId: string;
  title: string;
  authority: string;
  officialUrl: string;
  locator: { type: string; reference: string };
  excerpt: string;
  contentSha256: string;
}
```

RCL-GEN-2.0记录固定返回`caseNature: "synthetic"`和`policySources: PolicySource[]`。非RCL或人工案例不得被强制重写，原有内容优先保留。

### 10.2 公开案例页

- 页面名称改为“合成政策案例”。
- 删除“真实咨询记录”“真实社保规划案例”“真实咨询样本”等表述。
- 卡片展示地区、能力、人物条件摘要和咨询问题。
- 详情展示完整问答、计算日期、风险提示和政策依据。
- 官方URL使用安全外链属性；页面不得直接信任数据库中的任意HTML。

## 12. 原表受控改写设计

### 12.1 迁移边界

新增`0019_case_rewrite_audit.sql`，只创建审计结构，不在migration中更新案例业务数据。

`case_rewrite_batches`至少包含：`id/status/created_at/applied_at/created_by`、`code_sha/plan_hash`、来源与目标指纹、来源与目标生成器版本、来源manifest/attestation、政策快照绑定和行计数。`plan_hash`唯一，历史审计不得删除或原地改写。

`case_rewrite_entries`至少包含：batch、实体类型、实体ID、新旧UID、新旧内容hash、新旧snapshot hash、evidence hash和完整before/after JSON。batch、实体类型和实体ID组合唯一；hash为64位小写十六进制；外键不得级联删除历史审计。

### 12.2 CLI模式

- `audit`：只读核对案例、展示、回归测试、example、快照、release和证据。
- `plan`：生成确定性写集合、planHash和targetFingerprint。
- `apply`：在授权和全部绑定值一致时执行单事务更新。
- `verify`：逐行重算最终hash、来源链、数量和审计一致性。

### 12.3 apply前置条件

- 工作树干净且HEAD等于plan绑定的code SHA。
- 显式提供`--i-am-authorized`、planHash和targetFingerprint。
- 默认拒绝数据库名`policyops`；持久执行还需单独环境opt-in。
- 当前36 cases、36 showcases、36 regression tests、44 examples及快照指纹与plan一致。
- 所有引用artifact重新校验通过。

### 12.4 事务语义

1. 使用`REPEATABLE READ`事务并取得事务级advisory lock。
2. `FOR UPDATE`锁定36条case、36条showcase和36条regression test。
3. 事务内重算来源指纹、planHash和targetFingerprint。
4. 保留整数ID，更新V1→V2 UID及全部V2业务字段。
5. 清空回归测试旧`last_run_result/last_run_at`。
6. 写入一个rewrite batch和恰好108条before/after entry。
7. COMMIT前重读全部目标行并验证内容hash。
8. 任一不一致整体回滚。

同一计划复跑必须返回`noop:true`；只完成部分内容或审计不一致必须返回稳定state drift错误，禁止自动补写。

- **SHV2-NFR-001 确定性**：相同代码、证据、快照和输入生成逐字节一致产物。
